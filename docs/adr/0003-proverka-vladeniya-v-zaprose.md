# 0003. Проверка владения записью в запросе к БД

**Статус:** принято

## Контекст

Пользователи работают со своими записями. Нужно исключить доступ к чужим данным
по прямому идентификатору — классическая уязвимость IDOR.

## Варианты

1. **Фильтр по владельцу в запросе к БД** — чужая запись не выбирается вообще
2. **Выбрать по id, затем сравнить владельца в коде** — привычно, но ошибка в проверке
   открывает доступ
3. **Middleware или декоратор с проверкой прав** — универсально, но прячет логику
   доступа от того, кто читает роутер

## Решение

Вариант 1. Фильтр `WHERE id = ? AND owner_id = ?` выполняется на уровне запроса,
результат «не найдено» превращается в 404.

## Обоснование

- Ошибка становится структурно невозможной: нельзя «забыть» проверку,
  потому что без неё запрос просто не вернёт данные
- 404 вместо 403 не подтверждает существование чужой записи — по кодам ответа
  нельзя перебирать чужие идентификаторы
- Проверка видна прямо в коде обработчика: читающий сразу понимает правило доступа

## Последствия

- Условие владения дублируется в каждом запросе — принято сознательно,
  вынесено во вспомогательную функцию `_get_owned_item`
- При появлении ролей (администратор видит всё) правило потребует расширения
- Поведение закреплено тестами: попытка чтения, изменения и удаления чужой записи
  проверяется явно (`tests/test_items.py`)
